# orchestration-pack

Single source of truth for the founder's Claude Code orchestration: the `/sisyphus` and `/cloud`
skills, the Sisyphus subagents (each with its own model) and the Sisyphus hooks.

How it reaches sessions:

- **Cloud**: each project repo carries a bootstrap in `.claude/settings.json` (`./sync.sh --bootstrap <repo>`,
  once per repo). Its SessionStart hook, in cloud sessions only, clones this public repo into
  `~/.cache/orchestration-pack` and runs `sync.sh --session`, which copies skills, agents and hooks into
  `~/.claude` (skills and agents load at once). The Sisyphus hooks and the permission rules are declared in the
  repo's settings and run the `~/.claude` copy, so they apply from the first session. No setup script,
  no environment, nothing per Claude account.
- **Mac**: `./sync.sh --home`. The bootstrap entries do nothing outside the cloud.

Checked 2026-10-21 in a cloud container: the Mac's `~/.claude` and repo-declared plugins never reach a cloud
session; a container's own `~/.claude` does; `permissions.defaultMode` is honoured from `~/.claude/settings.json`
only (so Auto mode is not set by the bootstrap); a private repo not attached to the session cannot be cloned,
a public one can.

## Watching cloud sessions from the Mac

A cloud session cannot message a local one. Cloud sessions write their upward message as the
first line of `status.md` on `notes/<topic>-status`; the Orchestrateur (Mac or cloud) runs
`skills/cloud/scripts/watch-status.sh` (one `git ls-remote` every 15 s, no model call while
quiet) and is woken in about 15-20 s with that line. Details: `skills/cloud/SKILL.md` §4.

## Hooks

`hooks/sisyphus.sh` is registered for `UserPromptSubmit`, `PreToolUse`
(`Write|Edit|NotebookEdit|Agent`) and `Stop`:

- `/sisyphus` sessions: keyword detector, strict router write guard, Prometheus md-only,
  nested delegation rights from `skills/sisyphus/runtime/delegation.json`, bounded todo
  continuation (see `skills/sisyphus/SKILL.md` §4).
- Role guard, in every session: when `<project>/.omo/role` contains `router` (cloud
  Orchestrateur and Sous-orchestrateurs write it at start), the main session's
  `Write`/`Edit`/`NotebookEdit` outside `.omo/`, its memory dir and its scratchpad are denied;
  its subagents may still edit. `writer` (Pistes) or no file: no guard. A malformed or
  unreadable role file counts as `router`, and the deny message says so (empty, unexpected
  content or unreadable) instead of claiming it says `router`. Bash redirections are not a way
  around it (rule in `runtime/router.md`).

## Permissions (project settings only)

`settings.fragment.json` also carries `permissions` rules, added by `sync.sh --bootstrap` and `--project` (never
by `--home`, so other repos keep their behaviour). Cloud sessions read only the project
settings, and narrow allow rules are resolved before the auto mode classifier, so in Auto mode
these run without a prompt:

- `git push [--no-verify] origin <sha or ref>:refs/heads/notes/*` (fast-forward status, answers
  and handoff branches);
- `git push [-u|--no-verify] origin [HEAD:][refs/heads/]claude/*` and the same for `chore/*`;
- the cloud session tools of the `claude-code-remote` server: `send_message`, `list_sessions`,
  `get_session`, `create_session`, `archive_session`, `list_events`, `add_repo`.

Denied (deny beats allow, in every mode, for the founder too in that repo): any push with
`--force*`, `-f`, a `+` refspec, `--delete`/`-d`, an empty-source `:ref`, `--mirror`, `--prune`,
and any push naming `master` or `main`. Limits, from the official permissions doc: rules match
the command text, so `git -C <dir> push …` or `git push origin HEAD` while on master are not
matched (the classifier still judges them; the briefs never use those forms), nor is a
one-segment deletion `git push origin :foo` as the last argument (a rule ending in `:*` is read
as a trailing wildcard; `:a/b` and `:foo <more>` are denied); allow rules
cannot check that a `claude/*` branch is the session's own. Rules are added, never removed: a
rule dropped from the fragment must be deleted by hand from each repo's settings.

When the pack is installed both in `~/.claude` and in the project, the project copy runs and
the home copy steps aside.

## Sync

```bash
./sync.sh --project /path/to/repo    # into <repo>/.claude/, then commit .claude/ in that repo
./sync.sh --home                     # into ~/.claude/, after a backup to ~/.claude/backup-orchestration-<date>/
./sync.sh --cloud                    # into ~/.claude/ of a cloud container, with the permission rules and defaultMode auto
./sync.sh --check /path/to/repo      # OK or STALE
./sync.sh --bootstrap /path/to/repo  # once per repo: SessionStart bootstrap + hooks + permissions in <repo>/.claude/settings.json
./sync.sh --session                  # files only into ~/.claude (what the bootstrap runs)
```

It copies the tracked files of `skills/`, `agents/`, `hooks/`, merges `settings.fragment.json`
into `.claude/settings.json` with `jq` (other keys and hooks kept, managed Sisyphus entries
replaced, including the older direct `sisyphus_hooks.py` ones; with `--project`, the fragment's
permission rules are appended to `permissions.allow`/`permissions.deny` when missing), writes
`.claude/ORCHESTRATION_VERSION` (version, source sha, UTC date) and
`.claude/ORCHESTRATION_MANIFEST`, and deletes only files of the previous manifest that left
the source. Running it twice changes nothing. Requires `jq` and `git`.

## Update

1. Edit the sources here: `skills/sisyphus/runtime/*`, `scripts/build.py` (models, prompt
   rewrites), `scripts/hooks/sisyphus_hooks.py`, `skills/cloud/*`. Never edit `agents/` or
   `skills/sisyphus/modes/` by hand.
2. `python3 skills/sisyphus/scripts/build.py` (regenerates `agents/`, `modes/`, `teams/`).
3. `python3 -m unittest discover -s skills/sisyphus/scripts/hooks`
4. Bump `VERSION`, commit, push.
5. Merge into `main`: bootstrapped repos get it at their next cloud session. `./sync.sh --home` on the Mac.
   Re-run `--bootstrap` in the repos only when `settings.fragment.json` changed (hooks or permissions).

Excluded on purpose: `ocx-*` agents (route through the opencodex proxy to other models),
`council-*` agents (roast-room, not Sisyphus), secrets, `.env`, caches, and the vendored OmO
skills no prompt references (coding-agent-sessions, data-scientist, lsp-setup, programming,
ultimate-browsing, ulw-research).
